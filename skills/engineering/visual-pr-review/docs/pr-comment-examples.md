# What the PR comment looks like

When `--pr` is used, Visual PR Review always writes the proposed comment to
`visual-review-output/pr-comment.md` first. Nothing is published unless `--post-comment` is also
passed.

> **Current behavior:** the skill creates a PR comment. It does not replace or append to the pull
> request description.

The examples below use illustrative repository names and commit SHAs, but follow the Markdown
structure produced by the current renderers.

## Web or UI pull request

The published comment contains the verdict table, an attention list when needed, and the uploaded
side-by-side PNGs.

---

The image above is a real CLI-generated side-by-side artifact from a two-commit documentation
fixture, not a hand-drawn placeholder.

Without `--post-comment`, `pr-comment.md` contains the verdict table and attention list, but omits
the Evidence section. Its footer points reviewers to the side-by-side and diff images in the local
output directory.

With `--post-comment`, the CLI uploads each available side-by-side image, builds the image-bearing
version shown above, writes that exact version to `pr-comment.md`, and then posts it to GitHub.

## Backend or non-web pull request

With `--backend`, the comment contains a diff-derived change summary. No browser is started.

## Publication boundary

| Invocation | Result |
| --- | --- |
| `--pr <url>` | Writes `pr-comment.md` locally. No GitHub write occurs. |
| `--pr <url> --post-comment` | Uploads web evidence images and posts the generated comment. |
| `--pr <url> --backend` | Writes the backend summary comment locally. |
| `--pr <url> --backend --post-comment` | Posts the backend summary comment. The architecture SVG remains local. |

Human review remains authoritative. A generated verdict describes evidence, not approval.
